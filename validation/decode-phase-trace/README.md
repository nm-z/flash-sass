# Decode phase trace on the serving baseline (2026-10-18)

Goal context: ≥ 140 tok/s decode and ≥ 1,200 tok/s prompt processing on archy's
six serving dies. Every fresh chat pair recorded in gpuq so far measures 37–39.5
tok/s decode and 38–59 tok/s prompt processing; all were measured through the
chat endpoint and are recorded under `goal.decode.tokens_s` / `goal.prefill.tokens_s`.

## Measurement

- gpuq job `a2a63951-6fd7-415d-a38d-3df6445f2538` (`goal-baseline-decode-phase-trace`).
- Engine: the live `attention-q-release` library; image: the baseline `iq4-bias`
  `die.cubin` regenerated byte-for-byte (`IQ4_BIASED_DOT=1`, verified by SHA-256)
  and reassembled with `DIE_TRACE=1` as `die_trace.cubin`.
- `FLASH_TRACE=8`: the last prompt position plus seven generated positions, CTA 0
  of every die. Instrumented decode rate 38.06 tok/s, output tokens identical to
  the baseline fixture.
- Aggregation: `trace-breakdown.rb` (stored in gpuq job `goal-decode-phase-breakdown`
  with the full six-die report). Per phase: dispatch = wait_start − start,
  exchange wait = wait_end − wait_start, body = body_end − wait_end,
  barrier = end − body_end (includes the other fifteen CTAs' remaining work).

## Per generated token, die 0 (the other dies are within 0.1 ms)

| interval | ms | share |
|---|---:|---:|
| op bodies (CTA 0) | 14.22 | 55 % |
| exchange waits | 5.99 | 23 % |
| grid barrier + other CTAs' tail | 4.13 | 16 % |
| descriptor dispatch | 1.32 | 5 % |
| gaps between phases | 0.79 | 3 % |
| **total, 1,178 phases** | **25.66** | |

Per-phase fixed floor: ops with sub-3 µs bodies (`moesel`, `bf16bias`,
`conv1d`, `embrow`) still take 6–7.5 µs per phase; p50 of dispatch+barrier
alone is 3.1 µs, p90 8.2 µs.

## Where the waits are

- Twelve `actq256` phases per token wait 141–227 µs each for the attention die
  (layers 3, 7, …, 47): about 2.2 ms per token during which five dies idle. The
  attention die spends 124–204 µs per attention layer across 11 small phases
  (body 80–150 µs), so this is per-phase overhead on tiny ops, not attention
  arithmetic at this context length.
- `hcwsum` waits 1.8–2.2 ms per token for the slowest die's routed experts
  (expert split: the die holding the most of the token's ten experts gates the
  phase).
- 124 standalone `xsend` phases cost 1.6 ms, of which 1.0 ms is the send-side
  barrier (`MEMBAR.SYS` plus flag stores). Forty of them follow `q2moedn`,
  the rest follow row-split projections without an XOUT variant.

## Cold instruction fetch inside "body"

When an op immediately repeats, its second body is much shorter:

| op | first instance | repeated instance | difference | pairs/token |
|---|---:|---:|---:|---:|
| `q3kk2560` | 46.7 µs | 11.4 µs | 35.3 µs | 13 |
| `iq4k2560` | 43.4 µs | 12.4 µs | 31.0 µs | 2 |
| `q2k2560` | 24.7 µs | 7.6 µs | 17.1 µs | 1 |
| `q2moegn` | 15.0 µs | 10.8 µs | 4.3 µs | 48 |

The weights differ between the two instances, so the difference is not weight
caching; it matches the repo's earlier `PROG_DUP` observation (SPEC: "the first
run of an op pays ~5–12 µs of instruction fetch") but is larger for the K-quant
bodies. Maxwell SASS has no evict-first load hint (`ld.global.cs` assembles to a
plain `LDG.E` for sm_52), so the L2 cannot be steered to retain code.

## What this means for the target

7.1 ms per token (140 tok/s) needs all four buckets reduced together: the
per-phase overhead alone (barrier + dispatch + gaps ≈ 6.2 ms at 1,178 phases)
exceeds the whole budget, and the cold-fetch share of bodies is of the same
order. Kernel-local arithmetic changes that keep the phase structure, which is
what every candidate measured so far did, cannot move the full-model rate by
more than a few percent, and none did.
